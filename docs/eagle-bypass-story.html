Field report · Rainforest EAGLE-200 · linknode.com

The meter was fine. The cloud wasn’t. So we read the meter ourselves.

Our home energy dashboard kept going dark. The fault wasn’t the network and wasn’t the meter — it was the path in between. This is how we diagnosed it and built a small, self-effacing workaround that fills the gaps and gets out of the way the moment the normal path recovers. Written for two readers: the Rainforest firmware engineer who knows this device better than we do, and the fellow owner who just wants their graph back.

The pipeline

An EAGLE-200 reads a residential smart meter over Zigbee and uploads to Rainforest’s cloud, which forwards each reading to a webhook of our choosing. Ours lands at a small Flask collector on Fly.io, which writes to InfluxDB and renders a live gauge in Grafana.

the normal data path
smart meter ──Zigbee──▶ EAGLE-200 gateway ──HTTPS──▶ Rainforest cloud
                                                          │
                                                          ▼  HTTPS POST (XML)
   Grafana ◀── InfluxDB ◀── linknode-eagle-monitor.fly.dev/eagle

When it works, a reading arrives roughly every 8–10 seconds. When it doesn’t, every downstream stage is starved — and there is nothing any of them can do about it, because the reading never left the gateway.

The failure

The stalls began as an occasional annoyance and, after an abrupt step-change on 24 June 2026, became the normal state of affairs. The signature is specific and, once you’ve seen it, unmistakable: the gateway’s web server answers instantly while the process that actually serves meter data is wedged.

We eliminated the network methodically — moved the gateway to wired Ethernet, watched the traffic on the wire, confirmed the box was reachable throughout. The tell is that the device returns 503 from its own local HTTP server: the front end (lighttpd) is healthy and fast, but the CGI backend that reads the Zigbee data has died.

TCP  10.0.0.222:80  connect                   OPEN    5 ms  # network is fine

This is a device-internal fault. No amount of ret/rebooting the router, re-pairing Zigbee, or poking the cloud changes it; only power-cycling the gateway clears the wedge, and after 24 June it returns within the half-hour. The cloud portal, correctly, just reports the device as offline — it has nothing to forward.

The realization

Here is the part that turns a complaint into a project. The gateway exposes a local REST API on the LAN — the same one the cloud path is built on. And when the data CGI is having a good minute, that local API returns fully-formed, current meter readings, even while the cloud upload is stone dead.

The opening

The data never left the building. If we can read the meter locally and hand our own collector exactly what the cloud would have handed it, the dashboard never has to know the cloud was down.

What we built

A single, dependency-free Python script that polls the local API, translates each reading into the precise wire format our collector already parses, and POSTs it to the same /eagle endpoint — indistinguishable, from the collector’s side, from a genuine Rainforest forward.

The wire format, reconstructed

The collector expects raw Zigbee values — a hex integer plus a multiplier and divisor — and does the decimal arithmetic itself. So rather than send a finished number, we run that arithmetic backwards: take the decimal the local API gives us and re-encode the raw form, so the collector’s own math lands exactly on the original reading. One message type per POST, because the parser handles the first match and ignores the rest.

Two details are load-bearing, and both are the kind of thing you only learn by getting them wrong first:

Gotcha · time

The timestamp is Zigbee-epoch. Seconds are counted from 2000-01-01, not the Unix epoch — an offset of 946684800. Send a Unix timestamp and the collector’s sanity check quietly rewrites your reading’s time by 30 years.

Gotcha · identity

There are two radios. Tag the data with the control radio (…ef69). The other MAC (…ef68) only ever emitted empty frames, so the collector filters it outright — label your messages with it and they vanish on arrival.

Failover, not replacement

The workaround’s guiding principle is to do nothing when it isn’t needed. It watches the collector’s own freshness clock and ships only when the cloud path has gone quiet past a threshold, so healthy Rainforest traffic is never duplicated. Because our own uploads reset that same clock, it periodically falls silent for one cycle to check whether the cloud has genuinely recovered — if the clock stays fresh while we hold our breath, Rainforest is back, and we stand down.

It is also built for a flaky counterpart. The device’s data CGI flaps between clean reads, timeouts, 503s, and the occasional well-formed-but-empty response. The poller treats every one of those as “nothing to ship this cycle,” logs it, and tries again — it never forwards a garbage reading and never crashes on a bad one.

Two notes, two readers

For Rainforest engineering

This is a peer report, not a complaint. The fault is contained to the data-collection CGI: in a single window, wifi_status and system_query return 200 while device_list and device_query return 503 from the same lighttpd instance — a backend hang, not a connectivity or Zigbee-pairing issue.

Repro: leave a post-24-June gateway running; watch device_list over the local API; it wedges within ~15–25 min and recovers only on a power cycle. The cloud outage is downstream of this — the box has nothing to upload.

The bright spot is your own local API: it was a stable enough surface to build a reliable fallback on. Hardening the data daemon (or letting it self-restart on a stuck read) would fix the root cause for every EAGLE-200 owner at once.

For fellow EAGLE-200 owners

If your cloud data keeps dropping but the device is reachable, you are probably seeing this same wedge — and you can route around it. The gateway’s local API (POST /cgi-bin/post_manager, HTTP Basic auth) serves live readings straight off your LAN, no cloud required. Poll it, reshape the reading, and send it wherever you like.

It runs happily on hardware you already have lying around — ours lives on a Raspberry Pi. The whole thing is one standard-library Python file.

Security

Your Install Code is a credential: it authenticates the local API, and that API will hand back your Wi-Fi passphrase in plaintext. Never paste raw captures into a forum or ticket, and store the Install Code like the password it effectively is.

Where it runs now

The bypass lives on a Raspberry Pi 3 as a systemd service — enabled, restart-on-failure, and proven across a reboot. It sits in standby while Rainforest is delivering, activates within about 90 seconds when the cloud stalls, backfills from the meter reading by reading, and steps aside the moment the normal path returns. The underlying device fault is unchanged; what changed is that a half-hour outage is now a gap the graph never shows.
